# claimable-pool-lock

`claimable-pool-lock` is a generic lock for UDT-like pool cells that need to serve many claims without creating one output per recipient at mint time.

## Purpose

The lock owns a mutable claim list in its cell data.
It does not know anything about campaigns, quests, protocols, user cells, or any other application-specific identity scheme.

The paired type script is responsible for:

- authorizing the initial mint or pool creation
- deciding which asset type is carried by the pool cell
- deciding when a pool should exist

The lock is only responsible for:

- tracking which lock hashes are allowed to claim
- removing all entries for each claimant included in a claim transaction
- ensuring each claimant is present in the transaction inputs
- ensuring each claimant receives the full amount assigned to their removed entries
- preventing the pool cell from losing CKB capacity during a claim
- allowing a recycler authority to reclaim the pool

## State Model

The first 16 bytes of the cell data are treated as the remaining distributable amount.
The trailing bytes are owned by the lock and encode the claim list.

### Data Layout

```text
[16-byte remaining_amount]
[4-byte entry_count]
[entry_0]
...
[entry_n]
```

Each entry is:

```text
[32-byte claimant_lock_hash]
[16-byte amount]
```

## Lock Args

The lock args are a single raw 32-byte recycler lock hash:

```text
[32-byte recycler_lock_hash]
```

No pool identity is stored in the lock args.
If an application needs pool-level authorization, that must be enforced by the paired type script during mint or pool creation.

## Claim Transition

A valid claim transition must satisfy all of the following:

- the pool cell stays in the same lock group
- the remaining pool entries keep their original ordering
- all entries for one or more claimants are removed
- each claimant lock hash for the removed entries appears in the transaction inputs
- the pool amount decreases by exactly the sum of the removed entries
- each claimant's cells with the same type script increase by exactly that claimant's removed-entry sum
- the pool cell capacity does not decrease

This lock assumes the carried asset uses the first 16 bytes of its cell data as an unsigned little-endian amount.

## Molecule Schema

The lock maintains its own schema at:

`schemas/claimable-pool-lock.mol`

That schema is the single source of truth for the shared lock data layout.

- Rust types are generated by this crate's `build.rs`
- TypeScript codecs and like-types are generated inside this contract directory

Only the first 16-byte amount prefix remains outside the schema because it must stay directly readable by the paired asset type script.

### TypeScript Output

Run:

```bash
node scripts/generate-ts.js
```

This generates:

- `ts/generated/claimable-pool.json`
- `ts/src/generated/claimable-pool.ts`
- `ts/src/generated/index.ts`

Other packages may consume the built `ckb-claimable-pool-lock` package, but this contract owns the generation step.

## Recycle Transition

If the lock group has no output, the pool is being recycled.
In that case the transaction must contain an input whose lock hash matches the recycler lock hash from the lock args.

## Non-Goals

This lock does not:

- validate business-specific identities
- validate quest or campaign metadata
- validate pool provenance
- validate mint permissions
- validate non-standard token accounting rules
